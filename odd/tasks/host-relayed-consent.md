# Host-relayed operator consent

## Objective

Make Beacon approval and revocation operable primarily through an agent while preserving explicit human authority. Pharos will expose a runtime-neutral, machine-safe consent protocol, and a functional Pi adapter will present the exact pending action to the human inside Pi before completing it.

## Problem

The current lifecycle is safe but TTY-first. `pharos beacon approve` and `pharos beacon revoke` require direct interactive prompts, while the application accepts an `operatorConfirmed` boolean that is not a host-origin proof. An agent can inspect and report state, but it cannot drive the complete lifecycle through normal tool execution without either stopping for a separate terminal action or being trusted to assert the human decision.

Agent prose, model-generated arguments, unsigned JSON, and a bare confirmation boolean must never create approval or revocation authority.

## Why now

Issue #77 delivered immutable approval, truthful status, and reasoned revocation. The product is intended to be used mostly through an agent, with humans retaining authority at consequential boundaries. A host-relayed consent boundary is therefore required before readiness, task handoff, generation, execution, or verification are added.

## Product decisions

- Normal Pharos operation is agent-first; humans retain explicit approval, revocation, safety, and disposition authority.
- Approval and revocation consent are collected inside the agent host chat/UI, not by asking the human to run a separate terminal command for each action.
- The canonical consent contract remains runtime-neutral; Pi is the first functional adapter.
- V1 protects the supported host protocol: model messages, tool calls, and model-visible arguments/results cannot mint consent. A malicious process with arbitrary same-user shell/process access is explicitly outside this slice's threat model.
- Assurance remains honest `operator_confirmed`; the system does not claim cryptographic proof of human identity.
- A real Pi adapter is part of this slice. A protocol-only delivery is insufficient.

## Scope

### Included

- Versioned runtime-neutral consent request, decision/grant, refusal, and result contracts.
- Exact action binding:
  - approval: project, Beacon, draft ID, expected revision, semantic hash, request identity, and any required stale-origin acknowledgement;
  - revocation: project, Beacon, expected active version, normalized reason, and request identity.
- Expiring, single-action, one-time host grants.
- Trusted-host registration/provisioning compatible with the selected v1 threat model, with private material outside repository configuration and model-visible protocol results.
- Durable challenge state, consumption state, audit reference, idempotency, crash recovery, and concurrency behavior.
- Fresh-state revalidation before lifecycle mutation; stale consent refuses without mutation and requires a new request.
- Agent-safe JSON commands/envelopes for preparation and status; host-only Pi completion and recovery.
- A separate `integrations/pi/` package with a human-invoked Pi command/UI flow; no LLM-callable consent tool.
- Pi UI presentation of the exact action and binding, explicit approve/decline handling, non-TUI refusal, and capability secrecy from model context/results.
- Focused, integration, recovery, concurrency, stream-safety, and adapter tests.
- Product/spec/README updates that describe the new agent-first boundary and its threat model truthfully.

### Out of scope

- Resistance to malicious same-user shell/process inspection or tampering.
- Cryptographic proof that a specific natural person controlled the host.
- MCP or adapters for Claude Code, Codex, OpenCode, or other hosts.
- Operational readiness, task-package handoff, generation, execution, evidence, repair, or verification.
- Application-code mutation in target repositories.
- Production-target support.
- Merge, release, or production deployment; feature commits, branch pushes and PR creation were separately requested after implementation.

## Constraints

- Preserve hexagonal boundaries: CLI/integration adapters → application → domain.
- Preserve existing `BeaconStore` atomic authority checks, immutable history, replay behavior, and crash recovery.
- Never expose private signing/capability material through CLI stdout/stderr, Pi tool arguments/results, Pi model context, session entries, logs, or repository configuration.
- Human consent requests must be generated from canonical Pharos state, not from model-authored prompt text.
- The Pi action must be human-invoked and must refuse when no interactive TUI is available.
- A grant authorizes exactly one immutable action binding and expires. Changed action input, semantic state, signer, or challenge refuses.
- Same request identity and same canonical input may replay the original persisted result; changed input conflicts. A consumed grant cannot authorize a second mutation.
- Keep technical artifacts, code, tests, and public CLI copy in English.
- Do not modify the root checkout or its pre-existing `.gitignore` change.
- Do not add dependencies unless the implementation proves a concrete need.
- Review-size heuristic is approximately 400 authored changed lines per work unit; preserve coherent behavior and tests over cosmetic line limits.
